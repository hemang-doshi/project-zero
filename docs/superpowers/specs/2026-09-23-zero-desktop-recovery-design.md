# Zero desktop recovery and interaction design

**Status:** approved for implementation by the user on 2026-09-23. Implementation results and environment-gated follow-up work are recorded in the linked plans and current snapshot.

## Evidence and scope

The attached screenshot shows a light Zero Bot window with many repeated bordered Thinking rows, long command summaries, an open inspector carrying low-priority metadata, a registered-project warning, and a composer with a failed-send notice. The screenshot proves the visual state and messages, not the internal cause of that particular send failure. The attached text describing the previous build is background; current code and process state were checked separately. Source tip is `318b243` in both app branches. The HMR process uses `ProjectZero/dev-electron`; this Mac has no Zero daemon at the dev socket. The original checkout has unrelated dirty Go work that must remain untouched.

The intended product is a local-first cockpit. Zero Bot should be a usable Codex/OpenCode client, Desk should emphasize the current Spotify listening session, Runtime should show measured local machine history, and Skills Lab should distinguish discovered files from actual learned skills. Network and Airlock need no visual redesign in this project. Flight Recorder stays, with a short explanation in the plan and no feature change.

## Findings by surface

### Zero Bot

1. **Send path.** `ZeroBotRoute.tsx` submits a `{provider, model, threadId, text}` request to `prompt.submit`; `prompt-gateway.ts` scans it and `provider-dispatch.ts` calls Codex `thread/read` then `turn/start`, or OpenCode `session/load`, model selection and `session/prompt`. A blocked gateway decision has a specific reason, but `promptResult` replaces every blocked reason with “Review the destination and try again.” The exact cause of the photographed failure is unproven. The missing daemon explains `projects.list` failure; it does not by itself prove provider dispatch cannot work. `canSend` currently requires `openProject` for Codex, and the sidebar can form a synthetic cwd group even with no daemon. Verification must trace the selected thread, project/cwd binding, model, gateway outcome and provider response without logging prompt bodies or secrets.
2. **Reading and creation.** OpenCode sidebar rows come from read-only `~/.local/share/opencode/opencode.db`. Opening a row reads `session`, `message` and `part` records. `New conversation` immediately calls Codex `thread/start` or OpenCode `session/new` before there is a message. This creates visible empty sessions and makes the “no readable messages” notice normal for those sessions. OpenCode saved titles are displayed verbatim, including `New session` plus timestamp. Model options are populated only after a live ACP `session/load`; the selector can show a stale or unadvertised value before that.
3. **Transcript density.** `chat.model.ts` creates one thinking item per reasoning item; `ZeroBotChat.tsx` gives each item a bordered row and says “reasoning unavailable from provider” when neither text nor summary is present. Consecutive empty reasoning items therefore consume space while saying little. Command summaries also show unbounded paths/arguments in the collapsed view. The inspector is open by default and shows thread ID, counts, pending-feature copy, Airlock explanation and event data at the same visual weight. The font stack uses Inter without bundling it, and much UI text is 8.5–12px. Controls and transitions exist, but most content arrives as static blocks.
4. **Usage.** OpenCode usage is read from one saved session `info` shape and only appears if all four fields are numeric. Codex usage is not parsed or subscribed to at all. Public Codex app-server schema includes `thread/tokenUsage/updated` with input, cached input, output and reasoning output token counts. There is no verified monetary cost field in the inspected local path. Show token usage only from provider evidence; never calculate a fake price.
5. **Theme and organization.** Light/dark theme tokens, preference persistence, and a Settings switch already exist. The photographed light mode may be the saved/default selection; the issue to test is discoverability, coverage, hydration, contrast and packaged-app behavior. Codex threads are grouped by registered projects or cwd, but the groups are always expanded; OpenCode folders are likewise expanded. Folder paths and timestamps are prominent.

### Desk and Skills Lab

6. **Desk.** `DeskRoute.tsx` currently leads with focus session/project status, then Spotify metadata and bass trace, then a virtual desk display card. The virtual card appears when no display node is registered. It does not prove what the physical ESP32 will render or that delivery is reliable; the handoff records an unresolved hardware connection failure. The projected Spotify fields are state, track, artist, artwork and audio capture. There is no listening-session model, track history, playlist context, or playlist creation flow. Recenter the software Desk page on listening. Keep the existing physical display code and its explicit unverified state, but remove its virtual mockup from the primary Desk view.
7. **Skills Lab.** Discovery scans installed skill roots and two candidate `skills-learned` folders. No learner or persisted learned-skill writer exists in this app or daemon, so daily Codex use cannot itself create new entries. Earlier `Debug Zero`-style labels were fixtures or deterministic fallback, not evidence of a working learning pipeline. Skill/plugin icons are frontmatter text or generic glyphs, not verified brand artwork. The approved implementation should use a bounded, user-reviewed proposal and install flow for self-learned skills; no silent automatic model calls or scanning of unrelated folders. Brand icons need a curated source/provenance manifest, explicit unknown state, and tests for stale/missing assets rather than an invented logo.

### Runtime and shell

8. **Telemetry.** `telemetry.ts` reads `os.cpus()` and macOS `ps`, `vm_stat`, `sysctl`, `netstat`, `ioreg` in the Electron main process, at most once per second when requested. It does not poll Activity Monitor. `RuntimeRoute.tsx` starts a two-second visible-only pull when mounted; its graph arrays live in component state, so opening Runtime has no earlier history. The first CPU and byte-rate samples require a prior counter sample. GPU utilization is already sampled when `ioreg` exposes `Device Utilization %`, but it is only a footer string, not a fifth chart. No top-process model exists. Process-level disk/network attribution and memory-pressure attribution must be verified against available macOS counters before promising exact rankings.
9. **Status.** The yellow `RECONNECTING` badge is the daemon-backed cockpit stream state. In the isolated preview its socket is absent, and the Runtime header's `UNAVAILABLE` represents no daemon focus session. Machine telemetry should remain available separately. The UI currently makes these two independent states feel like one machine-data outage.
10. **Wallpaper.** A theme choice and custom wallpaper path are saved in the dev/production prefs profile. A custom image is referenced at its original path rather than copied into managed storage, so persistence depends on that external file continuing to exist and the same profile being used. The previous mixed launch altered layout preferences; there is no byte-for-byte backup. The new design should copy an explicitly chosen image into app-managed storage, keep the saved choice, and report missing/unreadable images honestly.

## Design decisions for approval

- Zero Bot starts with the conversation and composer. Collapse consecutive reasoning items into one compact, borderless accordion per contiguous run. Hide a run with no provider-visible content unless an active progress indicator is needed. Never invent model thoughts. Put commands in a genuine monospace output area when opened, with a short action label when collapsed.
- Inspector defaults closed and keeps the useful Calls by tool summary. Thread ID, timestamps, raw events and protocol metadata live in a Details disclosure. Airlock is a short current-state/history control, linked to the existing Airlock route. Keep failure states visible at the point of action.
- Folder groups are accessible accordions with session counts and preserved selection. Primary labels use meaningful provider titles or the first user message when available; timestamps are secondary metadata. Empty drafts stay local until the first send, subject to provider protocol and Airlock checks.
- Show verified Codex token totals and OpenCode saved usage when present. Cost is shown only when explicitly supplied and attributable by the provider. No estimated dollar amount.
- Desk's software view shows current track, session duration, ordered track history, source context and an explicit “Create playlist” action for eligible sessions. Listening-session boundaries, pause gaps, duplicate tracks and restart behavior require a defined local policy. Playlist creation requires user OAuth consent and a final explicit click; it must never run in the background. Keep the physical display transport untouched until a separate measured hardware acceptance test is possible.
- Skills Lab clearly labels installed, proposed and user-approved learned skills. With a visible opt-in, it may observe bounded local Codex/OpenCode history already available to the app and detect repeated workflows deterministically when the app is open. It drafts candidates with source references for review; it never installs a skill or invokes a model silently. With learning disabled, it reads only explicitly selected evidence. Brand artwork is accepted only from a verified local/plugin manifest or a curated official source; unknown is visibly unknown.
- Runtime's sampling owner moves to a bounded main-process ring buffer while visible app activity warrants it. Opening the route returns recent measured points immediately; no fabricated backfill. A fifth GPU chart uses measured values or an unavailable state. Top-process lists expose only metrics that can be attributed accurately on this macOS build.
- Motion should help navigation and state changes, respect reduced motion, and avoid continuous decorative animation or excess idle CPU. Typography needs a tested, consistent scale and a dependable installed/bundled font strategy. Network remains unchanged. Flight Recorder receives no code change in this scope.

## Acceptance and gates

The work is complete only when a fresh packaged preview can send and receive one explicitly authorized test turn through each available provider, with Airlock behavior verified and no false “sent” claim; empty drafts do not create provider IDs; model selection is based on the active provider's advertised options; a representative long transcript is readable at normal and narrow widths in light/dark modes; and the inspector can reveal metadata on demand. Runtime must show prior measured data on open after sufficient sampling, distinguish daemon outage from machine measurements, and keep GPU/process rankings honest. Desk must show a real listening session when authorized Spotify data exists and a clear unavailable state when it does not. Skills Lab must demonstrate proposal, review and persisted approved skill from isolated test data. Wallpaper must survive app restart and source-file removal after import. Existing full desktop tests, typecheck, targeted Go tests, manual visual review and physical checks where hardware is available are required. A build alone is not physical acceptance.

## External documentation check

Context7 resolved `/openai/codex` and `/websites/developer_spotify`, but docs retrieval failed with “Invalid or expired OAuth token”; the OpenCode library lookup failed with the same error. [Official Codex app-server schema](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/json/v2/ThreadTokenUsageUpdatedNotification.json) confirms the token-usage notification. Spotify's current API documents [current playback](https://developer.spotify.com/documentation/web-api/reference/get-the-users-currently-playing-track), [recent tracks](https://developer.spotify.com/documentation/web-api/reference/get-recently-played), [playlist creation](https://developer.spotify.com/documentation/web-api/reference/create-playlist) and [adding items](https://developer.spotify.com/documentation/web-api/reference/add-items-to-playlist). Exact ACP behavior remains a local-code hypothesis until an authenticated Context7 lookup or a read-only probe against the installed OpenCode 1.18.30 confirms it. Current Spotify docs use `POST /me/playlists` and `POST /playlists/{id}/items`; older `/tracks` playlist mutation is [deprecated](https://developer.spotify.com/documentation/web-api/reference/add-tracks-to-playlist).
